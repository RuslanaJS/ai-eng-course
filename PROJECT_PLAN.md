# PropDoc: план проєкту

2026-10-15 · Ruslana

> Цей файл синхронізований з документом «PropDoc: план проєкту» (джерело правди: документ). Остання синхронізація: 2026-10-22.

PropDoc — рушій «документи → аналітика» для ринку житла в Польщі: з «брудних» документів витягує структуровані дані, відповідає з цитатами, агентом збирає аналіз у вигляді віджетів і працює як API-сервіс. Це наскрізний курсовий проєкт AI Engineering: чотири кейси курсу це чотири етапи системи.

## Проблема й користувачі

Покупець чи інвестор у Польщі, особливо іноземець, збирає картину з розрізнених документів: проспекти девелоперів, звіти НБП і консалтингових компаній, закони про набуття нерухомості. Читати це вручну довго, а цифри з різних джерел складно порівняти.

| Роль | Що робить у системі | Що отримує |
|---|---|---|
| Покупець чи інвестор | ставить питання природною мовою | відповідь із цитатою (документ і сторінка) та віджет із порівнянням |
| Аналітик чи консультант | просить порівняння міст, районів, девелоперів | графік або таблицю з посиланням на джерело кожної цифри |
| Розробник-інтегратор (я і колеги) | викликає API і MCP-інструменти | JSON-відповіді, специфікацію віджета, OpenAPI-документацію |

## Що на виході

1. **Відповідь із джерелом.** Питання «Чи потрібен дозвіл громадянину не-ЄС для купівлі квартири?» дає короткий текст і цитату: документ, сторінка, фрагмент. Якщо даних у корпусі немає, система так і каже.
2. **Віджет аналітики.** Питання «Порівняй Варшаву й Краків за ціною за м² і термінами здачі» дає специфікацію віджета, яку рендерить проста HTML-сторінка. Кожна цифра має посилання на документ.
3. **Структурована база.** Таблиця витягнутих полів з усіх документів (DuckDB), з якої агент рахує агрегації.
4. **Сервіс.** FastAPI з ендпоінтами /extract, /ask, /agent, ключем доступу, лімітами, логами й лічильником вартості.
5. **Звіт.** Заміри по кожному етапу в README і REPORT.md: які рішення прийняті й чому.

Приклад специфікації віджета (числа умовні, формат уточнюємо на етапі 3):

```json
{
  "type": "bar",
  "title": "Середня ціна за м², PLN",
  "x": "city",
  "y": "avg_price_per_m2_pln",
  "data": [
    {"city": "Warszawa", "avg_price_per_m2_pln": 17500, "sources": ["prospectus_007.p3", "nbp_report.p12"]},
    {"city": "Kraków", "avg_price_per_m2_pln": 15200, "sources": ["prospectus_014.p2"]}
  ],
  "notes": "Дані з проспектів девелоперів, не юридична порада"
}
```

## Вимоги

> **Статус: чернетка.** FR і NFR нижче ще не затверджені, їх уточнюємо після замірів на етапі 1 і на заняттях наступних блоків.

### Функціональні

| ID | Вимога | Етап |
|---|---|---|
| FR-1 | Витяг полів про одну квартиру з тексту за схемою (Pydantic): назва ЖК, девелопер, адреса (вулиця, район, місто), термін здачі, площа, кількість кімнат, поверх, ціна за м² (діапазон), оздоблення, паркінг, зручності | 1 |
| FR-2 | Два провайдери за спільним інтерфейсом: Anthropic API і локальна модель (Ollama, лише для ДЗ1), заміна без зміни коду | 1 |
| FR-3 | Версіонування промптів (prompts/ + CHANGELOG), валідація виходу, одна спроба виправлення, логування моделі, версії промпту й параметрів семплінгу | 1 |
| FR-4 | Поля, яких немає в тексті, повертаються як null, а не вигадані | 1 |
| FR-5 | Індексація документів із метаданими (документ, сторінка) і пошук релевантних фрагментів | 2 |
| FR-6 | Відповідь на питання з цитатою (документ, сторінка); коли даних немає, відповідь «не знайдено» | 2 |
| FR-7 | Інструменти агента: пошук по документах, SQL по таблиці витягнутих даних (лише читання), калькулятор витрат на купівлю | 3 |
| FR-8 | Агент виконує багатокрокову задачу й повертає специфікацію віджета, валідовану Pydantic | 3 |
| FR-10 | API: /extract, /ask, /agent, автентифікація ключем, OpenAPI-документація | 4 |
| FR-11 | Мінімальна HTML-сторінка, що рендерить віджет із відповіді API | 4 |
| FR-12 | MCP-сервер PropDoc з інструментами search_docs, query_table (лише читання) і cost_calculator; агент викликає їх як MCP-клієнт, ті самі інструменти можна підключити до зовнішнього клієнта (наприклад Claude Desktop) | 3 |

### Нефункціональні

Цілі нижче стартові: після перших замірів на етапі 1 уточнюємо їх, а не підганяємо результат під цифри.

| ID | Вимога | Ціль |
|---|---|---|
| NFR-1 | Точність витягу на golden set (платна модель) | не менше 85% точності по полях схеми |
| NFR-2 | Невалідні відповіді після спроби виправлення | не більше 5% |
| NFR-3 | RAG: чи знайдено правильний фрагмент | hit rate@5 не менше 80% на 25 питаннях |
| NFR-4 | RAG: чи відповідь спирається на джерело | faithfulness не менше 90% |
| NFR-5 | Агент: сценарії, виконані правильно | не менше 7 з 10 |
| NFR-6 | Вартість | менше $0,02 на запит /ask; відома вартість 1000 документів витягу |
| NFR-7 | Затримка | /ask p95 до 15 с (уточнюємо після замірів) |
| NFR-8 | Безпека | ключі лише в .env; інструменти MCP лише з переліку дозволених, SQL тільки читання, ліміт на розмір результату; захист від промпт-ін'єкцій у документах; без персональних даних у корпусі; застереження «не юридична порада» |
| NFR-9 | Відтворюваність | запуск однією командою (make run), залежності зафіксовані в uv.lock, дані завантажуються скриптом |
| NFR-10 | Якість процесу | eval-скрипт на кожному етапі; ruff і pytest у GitHub Actions |

## Дані

| Тип | К-сть | Мова | Джерело |
|---|---|---|---|
| Проспекти девелоперів (prospekt informacyjny) | 30-40 | PL | сайти девелоперів, список девелоперів з dane.gov.pl |
| Звіти (НБП, JLL, Colliers, Savills, Knight Frank, Otodom Analytics) | 15-25 | EN/PL | сайти організацій |
| Закони й роз'яснення (набуття нерухомості іноземцями, закон про девелоперів) | 5-10 | PL | isap.sejm.gov.pl, МВС |

На етапі 1 корпус складається зі сторінок квартир з rynekpierwotny.pl (29 шт.) і кількох ринкових текстів без квартири для перевірки на вигадування (4 шт.). Повні проспекти, звіти й закони з'являються на етапі 2. Навмисно залишаємо складні випадки: таблиці, частину сканів, змішані мови, відсутні поля. Не скрейпимо Otodom і OLX (ToS). Завантажені файли зберігаємо локально, у маніфесті фіксуємо URL і дату.

## Архітектура

```
документи (PDF, текст)
  -> парсинг і чанкінг
  -> екстрактор (схема Pydantic; Anthropic, локальна Ollama лише в ДЗ1) -> таблиця полів (DuckDB)
  -> індекс фрагментів (embeddings)

питання -> агент (MCP-клієнт) -> MCP-сервер (пошук, SQL, калькулятор) -> специфікація віджета + цитати
  -> API (FastAPI) -> HTML-віджет
```

Ключові рішення:

- Схема спершу руками в Pydantic (домашка 1). Інтерфейс екстрактора приймає будь-яку Pydantic-модель, тому конфіг домену додається поверх без переписування.
- Поза скоупом (ідея на майбутнє): конфіг домену описує поля, типи, одиниці й метрики. З нього генеруються модель, промпт і валідація. Приклад:

```yaml
domain: developer_prospectus
fields:
  - name: city
    type: string
  - name: price_per_m2
    type: number
    unit: PLN
    description: Average offer price per m2 of usable area
  - name: finish
    type: enum
    values: [developer_standard, turnkey, to_renovate, not_stated]
metrics:
  - name: avg_price_per_m2
    from: price_per_m2
    agg: avg
    group_by: [city]
```

- Документи це дані, а не інструкції: текст із документа ніколи не виконується як команда (захист від промпт-ін'єкцій).
- Агент не рахує на око: цифри беруться з таблиці витягнутих даних, ставки податків і зборів лише з документів корпусу.
- Моделі за етапами: екстракція (етап 1) на Haiku, бо задача проста і Haiku 4.5 дає 100% на golden set. На етапах 2-3 (відповідь із цитатою, робота агента) порівнюємо Haiku з Sonnet за якістю, вартістю й затримкою. Sonnet 5.5 не приймає нестандартну температуру, тому моделі порівнюємо на стандартних налаштуваннях.

## Етапи (за календарем курсу, 3-4 год/тиждень)

Календар курсу: блок 1 «Основи LLM» (заняття 1-5) до 27.10, блок 2 «Дані та RAG» (6-10) до 13.11, блок 3 «Агенти та MCP» (11-14) до 02.12, блок 4 «Продакшн» (15-18) із Demo Day 10.12. Між ДЗ3 і Demo Day лише 8 днів, тому каркас сервісу (FastAPI, Docker, CI) закладаємо вже на етапі 3.

### Етап 1: Витяг (до 27.10, кейс 1)

Чекпоінт 24.10, дедлайн 27.10. Покроковий план: документ «Домашка 1: Structured Extraction Service».

- **Що будуємо:** схема OfferRecord (одна квартира), 30 «брудних» текстів, golden set з 10 текстів, екстрактори на Anthropic Haiku і qwen2.5:3b в Ollama за спільним інтерфейсом, версії промптів, валідація з однією спробою виправлення, логування.
- **Вихід:** репо з тегом v0.1; results/ із виходами моделей; REPORT.md із таблицею «модель × версія промпту × семплінг» (точність по полях, % валідних, latency p50/p95, вартість на 1000 документів), розбір 3-5 помилок і вибір моделі.
- **Готово, коли:** FR-1..FR-4 виконані, NFR-1 і NFR-2 виміряні, `make run` працює з нуля.

### Етап 2: RAG і тести (до 13.11, кейс 2)

- **Що будуємо:** розширення корпусу до повних документів; парсинг PDF (текстові, частина із таблицями й сканами); чанкінг по сторінках і секціях із метаданими; embeddings (порівняти API і локальну модель, на 8 ГБ памʼяті); векторний індекс; пошук top-k; відповідь із цитатою (документ, сторінка) і відмова, коли даних немає.
- **Набір тестів:** 25 питань трьох типів: факт з одного документа, порівняння кількох документів, питання без відповіді в корпусі; частина польською, частина англійською.
- **Вихід:** скрипт побудови індексу; eval/questions.json з еталонами; eval/run_rag_eval.py; таблиця метрик (hit rate@5, faithfulness, коректність) для двох конфігурацій (розмір чанка, top-k) і двох моделей генерації (Haiku, Sonnet); тег v0.2.
- **Готово, коли:** FR-5 і FR-6 виконані, NFR-3 і NFR-4 виміряні однією командою.

### Етап 3: Агент, MCP і віджети (до 02.12, кейс 3)

- **Що будуємо:** агентний цикл з лімітом кроків і логуванням кожного виклику інструмента; три інструменти: search_docs (RAG), query_table (SQL по DuckDB, лише читання), cost_calculator (податки, нотаріус, комісія зі ставками з корпусу); усі три винесені в MCP-сервер (stdio), агент працює як MCP-клієнт, а ті самі інструменти можна підключити до зовнішнього клієнта; схема специфікації віджета в Pydantic (типи bar, line, table) і прототип рендера.
- **Сценарії перевірки (10):** порівняння двох міст за ціною й терміном; який девелопер здає найраніше; умови купівлі для не-ЄС; розрахунок витрат на купівлю; питання поза корпусом (агент має відмовити); спроба промпт-ін'єкції в документі.
- **Вихід:** модуль агента; eval/scenarios.json; звіт зі сценаріїв (успіх, кількість кроків, вартість) для Haiku і Sonnet; приклади віджетів; тег v0.3.
- **Готово, коли:** FR-7, FR-8 і FR-12 виконані, NFR-5 виміряний.

### Етап 4: Сервіс (до Demo Day 10.12, кейс 4)

- **Що будуємо:** FastAPI з /extract, /ask, /agent; автентифікація ключем і rate limit; валідація входу (розмір, тип файлу); захист від промпт-ін'єкцій (документи як дані, перевірка виходу, тест із «отруєним» документом); структуровані логи; лічильник токенів і вартості на запит; простий моніторинг (помилки витягу, вартість за день); Docker; GitHub Actions (ruff, pytest); HTML-сторінка з віджетом.
- **Вихід:** сервіс, що піднімається однією командою (docker); README з архітектурою й результатами замірів; тег v0.4; демо на 3-5 хвилин.
- **Готово, коли:** FR-10 і FR-11 виконані, NFR-6..NFR-10 перевірені.

## Сценарій демо (3-5 хвилин)

1. Питання про умови купівлі іноземцем і відповідь із цитатою.
2. Порівняння двох міст і віджет, де видно джерела цифр; ті самі інструменти викликає зовнішній клієнт через MCP.
3. Таблиця замірів: Haiku і Sonnet за точністю, вартістю й latency (локальна qwen лише як експеримент із ДЗ1).
4. Лічильник вартості й логи запиту.

## Ризики

- Розповзання скоупу: MCP мінімальний: один власний сервер, три інструменти, stdio; другий домен і конфіг домену не робимо.
- Вартість і ліміти платного API: лічильник токенів і вартості, кеш повторних запитів, дешевша модель для витягу (локальна модель була лише в ДЗ1).
- Мало еталонів: розмічаємо лише golden set (10) і 25 питань для RAG.
- Нестабільні джерела: файли зберігаємо локально, у маніфесті URL і дата.
- Юридична тема: завжди застереження, що це довідка, а не юридична порада.
- Обмеження ноутбука (M1, 8 ГБ): локальна модель лише для ДЗ1, embeddings можуть піти через API.

## Відкриті питання

- MCP: який транспорт і який зовнішній клієнт показуємо на демо: уточнити на заняттях 11-14.
- Embeddings: API чи локально.
- Фінальний формат специфікації віджета (Vega-Lite чи власний простий).
